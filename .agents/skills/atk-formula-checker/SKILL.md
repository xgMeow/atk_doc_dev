# ATK Markdown 公式检查与修复工具

## 何时使用

当用户提出以下任一请求时，应激活此 skill：

- “检查公式”
- “修复公式渲染失败”
- “检查 Markdown 公式格式”
- “检查 VuePress 公式是否能渲染”
- “把 `\\[...\\]` 改成 `$$...$$`”
- 用户指出 ATK 文档中的 LaTeX、MathJax、KaTeX 或 Markdown 公式显示异常
- 用户要求检查或修复 ATK 文档仓库中的公式分隔符、块级公式、行内公式或公式空行问题

## 检查范围

默认只主动检查以下 Markdown 文档目录：

- `01-安装`
- `02-案例教程`
- `03-基础使用指南`
- `04-理论基础`
- `5.专业使用指南`
- `二次开发教程`
- `发布说明`

如果用户明确指定文件或目录，以用户指定范围为准。

不要主动扫描以下目录：

- `node_modules`
- `.vuepress/.cache`
- `.vuepress/.temp`
- `dist`
- 其他构建产物或依赖目录

## 核心原则

1. **默认检查并修复**：发现确定会影响 VuePress 渲染的公式格式问题时，直接修复。
2. **跳过代码内容**： fenced code block、行内代码、缩进代码块中的示例公式不修改。
3. **只改公式格式**：不改公式含义、变量名、单位、上下文文字或章节结构。
4. **块级公式独占行**：块级公式使用 `$$`，并与正文、列表、图片、表格之间保持空行。
5. **行内公式保持行内**：短符号、变量和句内公式使用 `$...$`，不要拆成块级公式。
6. **不确定不乱改**：无法判断是公式、货币符号、路径、代码还是普通文本时，保留原样并在最终报告中说明。
7. **改后必须构建**：完成确定性修复后，必须执行 `npm run build:standalone` 验证。

## 公式格式规范

### 块级公式

块级公式必须使用独占行的 `$$` 包裹：

```markdown
$$
\varepsilon_{true} = \varepsilon_{mean} + \Delta\varepsilon
$$
```

不要使用 `\\[...\\]` 作为块级公式分隔符。

**转换示例**：

```markdown
\[F_{AE}(t) = F_{Fixed}(t_0), \quad \forall t\]
```

转换为：

```markdown
$$
F_{AE}(t) = F_{Fixed}(t_0), \quad \forall t
$$
```

### 行内公式

句子中的短公式、单个变量或符号使用 `$...$`：

```markdown
当 $\Delta\varepsilon$ 增大时，误差随之增大。
```

不要使用 `\\(...\\)` 作为行内公式分隔符。

**转换示例**：

```markdown
当 \(\Delta\varepsilon\) 增大时，误差随之增大。
```

转换为：

```markdown
当 $\Delta\varepsilon$ 增大时，误差随之增大。
```

## 自动修复规则

### 1. 修复 `\\[...\\]` 块级公式

将 `\\[...\\]` 改为独占行 `$$...$$`。

如果原公式单独占一行：

```markdown
\[ a^2 + b^2 = c^2 \]
```

修复为：

```markdown
$$
a^2 + b^2 = c^2
$$
```

如果原公式嵌在段落中，但公式内容明显是复杂公式或包含 `\\frac`、`\\sum`、`\\int`、`\\begin`、`\\left`、`\\right`、`\\quad`、换行、对齐环境等块级特征，将公式拆为块级公式，并保持前后正文为独立段落。

### 2. 修复 `\\(...\\)` 行内公式

将 `\\(...\\)` 改为 `$...$`：

```markdown
速度为 \(v\)，时间为 \(t\)。
```

修复为：

```markdown
速度为 $v$，时间为 $t$。
```

### 3. 规范块级公式空行

块级公式前后各保留一个空行：

```markdown
上一段文字。

$$
E = mc^2
$$

下一段文字。
```

列表项中的块级公式应保持在该列表项上下文中，不破坏缩进：

```markdown
1. 计算误差：

   $$
   e = x - \hat{x}
   $$

2. 分析结果。
```

### 4. 避免误改美元符号

不要把以下内容当作公式修复：

- 价格或货币：`$100`、`100$`
- Shell 变量：`$PATH`、`${HOME}`
- 模板变量：`${name}`
- 代码片段、命令、路径或配置值中的 `$`
- 未成对且无法确认意图的 `$`

### 5. 保留合法公式内容

不要更改公式内部内容，例如：

- 下标、上标、希腊字母、函数名
- `\\quad`、`\\forall`、`\\Delta`、`\\varepsilon`
- `aligned`、`matrix`、`cases` 等 LaTeX 环境
- 公式中的空格，除非它们只来自分隔符边界

## 工作流程

### 第1步：确认检查范围

- 如果用户指定文件，优先检查指定文件。
- 如果用户没有指定范围，检查“检查范围”中列出的 Markdown 文档目录。
- 使用文件搜索时排除依赖和构建产物目录。

### 第2步：扫描公式问题

查找以下模式：

- `\\[` 和 `\\]`
- `\\(` 和 `\\)`
- 不独占行的块级 `$$`
- 块级公式前后缺少空行
- 明显未闭合的 `$...`、`$$...$$`、`\\(...\\)`、`\\[...\\]`

扫描时必须跳过：

- fenced code block：三反引号或三波浪线之间的内容
- 行内代码：反引号包裹的内容
- 缩进代码块
- 纯示例说明中明确要求展示错误写法的内容，除非用户要求连示例也改

### 第3步：逐条修复确定性问题

按以下优先级修复：

1. `\\[...\\]` → 独占行 `$$...$$`
2. `\\(...\\)` → `$...$`
3. 块级公式前后空行
4. 明显未闭合或分隔符混用的问题

修复时使用最小改动，不顺手格式化无关内容。

### 第4步：构建验证

完成确定性修复后运行：

```bash
npm run build:standalone
```

要求：

- 构建成功后，才能认为公式修复完成。
- 如果构建失败，阅读错误信息并定位是否由公式格式导致。
- 如果失败原因是确定性公式问题，继续修复并重新构建。
- 如果失败原因与公式无关或无法确认，向用户说明构建失败原因，不要声称验证通过。

## 不自动修复规则

以下情况只报告，不修改：

- 公式分隔符疑似在代码示例中。
- `$` 可能表示货币、Shell 变量、模板变量或普通文本。
- 公式跨越复杂 Markdown 结构，自动拆分可能改变语义。
- 多处公式分隔符嵌套，无法确定正确边界。
- 用户明确要求只检查不修复。

## 最终报告格式

如果修复完成且构建通过，简短说明：

```markdown
公式检查和确定性修复已完成，`npm run build:standalone` 构建通过。没有需要你确认的不确定公式。
```

如果存在不确定公式，使用以下格式：

```markdown
公式检查和确定性修复已完成，`npm run build:standalone` 构建通过。以下公式需要你确认：

1. `文件路径:行号`
   - 原内容：`...`
   - 不确定原因：...
   - 建议：...
```

如果构建未通过，使用以下格式：

```markdown
已完成能确认的公式修复，但 `npm run build:standalone` 未通过。

构建失败原因：...

以下公式或问题需要你确认：

1. `文件路径:行号`
   - 原内容：`...`
   - 不确定原因：...
   - 建议：...
```

## 禁止事项

- 禁止修改代码块中的示例公式，除非用户明确要求。
- 禁止把所有 `$...$` 批量改成块级公式。
- 禁止把货币、Shell 变量或模板变量误判为公式。
- 禁止改动公式含义或变量名称。
- 禁止为了统一风格而修改本来能正确渲染的公式内容。
- 禁止跳过 `npm run build:standalone` 后声称验证完成。
